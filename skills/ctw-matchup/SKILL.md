# CTW matchup

Workflow version 1.2.0. Use the installed CTW Advisor connector. Inspect the tools actually callable in this conversation and their schemas; tool-name prefixes may vary. Repository code, a deployed endpoint, tool counts or a successful old-tool call do not prove a new tool is callable here. Never fabricate calls, substitute remembered unit stats, or build another backend.

## General lookup and roster queries

For roster enumeration, stat filters, sorting or mount-family lists, use `discover_unit_fields` and `search_units` only when both are callable. Read [lookup semantics and examples](references/lookup.md). If either is missing, report the specific capability gap; repeated guessed-name resolution cannot establish a complete roster. A metadata refresh or separate HTTP test is not connected-conversation acceptance.

1. Call `discover_unit_fields` for available fields, meanings, units, operators, null semantics and capabilities. Page relevant categorical values (for example subculture, caste or tactical category) before choosing exact keys. Do not guess unsupported fields.
2. Build `search_units` filters with explicit AND/OR grouping and discovered operators; choose selected fields, scalar sort and `variants` or `families` mode. Clarify material category/unit ambiguity. Keep base source stats separate from conditional effects.
3. Follow every `next_cursor` with identical query arguments until `complete:true` before claiming an exhaustive result. Preserve snapshot identity and check counts, unique keys and profile-versus-family count units. Completeness covers the imported snapshot only.
4. Families contain only matching variants, each with its own stats. Keep source aliases and roster memberships distinct from campaign recruitment or custom-battle selectability. Follow returned keys into `resolve_unit`, `get_unit_combat_profile` and the tactical workflow as needed; a lookup alone requires no combat evaluation.
5. Report the filter, scope, units, snapshot and meaningful limitations. Unsupported legendary/special classification is unknown; untranslated source labels retain stable keys. Never silently convert native speed or missing values.

## Resolve the question

1. Identify both intended units and the tactical decision. Call `resolve_unit` for each name or key. Display qualified names/variants. If ambiguous, present candidates and obtain selection before evaluation. If a colloquial family name could mean shielded/unshielded, mounted/unmounted, or elite variants, clarify that choice even if the plain label resolves. Never silently choose a candidate. Not-found is not proof the unit is absent: request an exact name/key or retrieve a source-backed candidate.
2. Clarify only material scenario choices. For a baseline, state assumptions and proceed: unmodified custom battle, ultra, rank 0; flat unobstructed ground, front facing, separation 200 m, horizon 120 s, both approach, fire/fight enabled. These are illustrative settings, not observations. Respect supplied orders, distance, contact assumptions and duration. Hosted duration is at most 300 s.
3. Call `get_matchup_evidence` with resolved identities. Inspect components, weapon/projectile/explosion relationships, attributes, relevant abilities and coverage. Use section pagination, `get_detail`, and `get_provenance` for consequential omitted evidence. A truncated or unrequested section is not absent mechanics. Keep artillery crew and engine separate. Do not apply listed passives/activated abilities to base stats yourself.

## Calculate and test the decision

4. Call `evaluate_single_unit_matchup` with the same identities and explicit scenario. The shared calculator owns numeric combat predictions. Read snapshot, model version, source facts, assumptions, empirical calibration, timing, both ledgers, verdict, sensitivity, unresolved inputs and limitations. Preserve nulls and scoped patch differences. On incompatible/unavailable data, give the exact diagnostic and what must be restored; never mix snapshots or fill gaps with memory.
5. Inspect material passives before accepting a base-only projection. If the actual evaluator schema exposes `sides.a/b.passives`, use sourced keys and explicit initial-state assumptions; do not add bonuses by hand. Read [conditional passive scenarios](references/passives.md). For Strength in Numbers on a full-health bearer, assume initially active, equality active, and reactivation unresolved; calculate that supported initial phase and compare an otherwise identical disabled case. State these assumptions; uncertain later transitions do not require a blocking question or erase the initial calculation. Check returned effective inputs, effect phases, source references and omitted/unsupported coverage. If the callable schema lacks passive support, prominently label the result **“base stats only; Strength in Numbers omitted”** (substitute the actual effect), report the capability gap, and do not claim the passive was calculated. Installed guidance or repository tests do not prove deployment.
6. Read [calculation interpretation](references/calculation.md) for defaults, ranged scheduling, projectile-count ambiguity and stopping semantics. Disclose consequential uncalibrated assumptions. Do not ask the user for technical source fields obtainable from tools.
7. Run a decision-relevant controlled variation, keeping other inputs fixed: separation/orders for approach, facing for shields, contacts for melee, or a defensible uncertain firing input. Report actual changed results. For material immediate-arrival ranged damage, rerun with the shooter's returned cycle as an illustrative flight delay. For unresolved projectile counts, inspect factors and compare explicit interpretations per the reference. Never select an interpretation merely because it produces a preferred outcome.

## Give tactical advice

Lead with the action the evidence supports and its conditions. Explain relevant identity and source/model version; baseline assumptions; time to range/contact; both sides' modeled damage (direct, explosion, melee and barrier absorption where relevant); distinct stopping criteria; conditional verdict and decisive sensitivity. Round prose numbers sensibly, retaining raw outputs for audits. Report an indeterminate verdict as indeterminate, even if its fallback point ordering names a side. Sensitivity corners are not confidence intervals.

Separate calculated changes from qualitative advice about obstruction, flanking, support, fatigue, abilities or terrain physics the model does not simulate. Never turn health depletion into routing, crew loss into established engine disablement, or projected health advantage into a guaranteed battle winner. Explain consequential gaps without burying useful results in every possible caveat.

For battle tests, save exact scenario and prediction before play, then compare measured outcomes separately. Connector/CLI agreement establishes reproducibility, not game accuracy. Calibration stays distinct from source facts.
